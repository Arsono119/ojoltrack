## 2. Opsi Feature yang Direkomendasikan (Inspirasi Domain Ojol)

> Semua opsi di bawah compatible dengan filosofi OjolTrack: mobile-first, <10 detik/entri, PWA offline, snake_case + LocalStorage.

### Opsi A — 🎯 Target Harian & Progress Tracker
**Ide:** User set target bersih harian (mis. Rp 150.000). Dashboard tampil progress bar, sisa ➜ tercapai, streak hari.
- **Pro:** Paling requested driver ojol; motivasi harian; implementasi UI ringan; viral untuk screenshot progress.
- **Kontra:** Bisa jadi pressure jika target tidak realistis; butuh UX untuk edit target & reset harian.
- **Impact Data Model:** Entitas baru `TargetHarian` atau single key `ojoltrack_target = { nominal_harian, updated_at, mode: "harian"|"mingguan" }` — tidak ubah `Transaksi`. Tambah `lib/target.ts` + calc `progress = pendapatanBersih / target`.
- **Estimasi Effort:** S (1-2 hari). File baru: `lib/target.ts`, `components/TargetCard.tsx`, `app/pengaturan/page.tsx` (atau modal di dashboard).

### Opsi B — ⏰ Pengingat & Notifikasi Lokal (Reminder)
**Ide:** Reminder isi transaksi jika jam tertentu belum ada order, atau pengingat jam cuan berdasarkan `histogramJam`.
- **Pro:** Mencegah lupa catat (pain point utama); pakai Notification API / Serwist — tetap PWA tanpa backend.
- **Kontra:** Izin notifikasi sering ditolak; tidak bisa background sync 100% reliable di iOS PWA.
- **Impact Data Model:** Key baru `ojoltrack_reminders = { enabled, jam: string[], last_prompt_at }`. Tidak ubah `Transaksi`. Perlu `lib/reminder.ts` + permission handling.
- **Estimasi Effort:** M (2-3 hari). Risk: perlu testing cross-browser PWA notification.

### Opsi C — 📤 Export Lanjutan & Sharing Visual
**Ide:** Export PDF rekap mingguan/bulanan + share image ringkasan (Canvas → PNG) untuk WhatsApp/IG Story.
- **Pro:** Driver suka pamer penghasilan bersih; CSV existing belum visual; bisa reuse `aggregateByDay` + Recharts → image.
- **Kontra:** PDF generation berat di client (jspdf/html2canvas); layout print perlu desain.
- **Impact Data Model:** Tidak ubah model — read-only dari `Transaksi`. Tambah `lib/exportPdf.ts`, `lib/shareImage.ts`.
- **Estimasi Effort:** M (3-4 hari). Alternatif MVP: mulai dengan PNG share dulu, PDF later.

### Opsi D — 🏷️ Kategori & Platform Custom + Anggaran Bulanan
**Ide:** User tambah kategori pengeluaran custom (mis. "parkir", "pulsa") dan platform custom (mis. "Maxim", "InDrive"), plus anggaran per kategori per bulan.
- **Pro:** Fleksibel untuk driver multi-platform; anggaran membantu kontrol pengeluaran makan/bensin.
- **Kontra:** Merusak enum strict `Platform`/`Kategori` di `types.ts` — perlu migrasi schema; UI tambah kompleks.
- **Impact Data Model:** Breaking light: `Platform` & `Kategori` jadi `string` (free-form) + whitelist default, simpan `ojoltrack_meta = { custom_platforms, custom_kategoris, anggaran: {kategori: nominal} }`. Validasi Zod perlu dilonggarkan ke `z.string()`.
- **Estimasi Effort:** M-L (4-5 hari). Risk: migrasi data lama `Lainnya` → custom.

### Opsi E — 🧠 Insight & Rekomendasi Pintar
**Ide:** Insight otomatis: "Jam 18-20 paling cuan Grab Rp 4.200/km", "Shopee Drive 12% lebih untung minggu ini", saran jam narik.
- **Pro:** Differentiator kuat; reuse `histogramJam` + `ringkasanHarian` — murni logic tanpa model baru.
- **Kontra:** Jika data tipis (<7 hari) insight bisa menyesatkan; butuh copywriting hati-hati.
- **Impact Data Model:** Tidak ubah model — layer `lib/insight.ts`. Tambah `components/InsightCard.tsx` di dashboard & grafik.
- **Estimasi Effort:** S-M (2 hari). Bisa jadi quick win pertama.

### Opsi F — ☁️ Backup, Restore & Sinkronisasi Ringan
**Ide:** Export/Import JSON terenkripsi + backup otomatis ke Google Drive / file, plus proteksi kehilangan HP.
- **Pro:** Critical untuk LocalStorage-only app; user takut kehilangan data; sudah ada `storage.exportJSON/importJSON` — tinggal UI.
- **Kontra:** Tanpa backend, sync antar device tetap manual; Google Drive butuh OAuth (scope sensitif).
- **Impact Data Model:** Tidak ubah `Transaksi` — tambah key `ojoltrack_backup_meta`. MVP cukup UI untuk `exportJSON` + `importJSON` dengan preview/duplikat handling (sudah ada `skip` logic).
- **Estimasi Effort:** S (1 hari untuk JSON UI), L jika Drive OAuth.

### Opsi G — 🔥 Streak, Gamifikasi & Kalender Heatmap
**Ide:** Kalender heatmap (GitHub-style) + streak hari narik + badge "7 hari cuan >100k".
- **Pro:** Gamifikasi ringan meningkatkan retensi; visual menarik untuk portofolio; data sudah ada (tanggal).
- **Kontra:** Risiko over-engineering; butuh kejelasan reward (tidak ada monetisasi lagi).
- **Impact Data Model:** Key baru `ojoltrack_streak_meta` atau derived saja dari `Transaksi` (tanpa simpan). Paling aman derived.
- **Estimasi Effort:** S-M (2-3 hari).

### 3.5 Pertanyaan Klarifikasi untuk User
> Wajib dijawab sebelum masuk fase Plan → Build.

1. **Platform fokus:** Apakah feature ini untuk semua platform (Grab + Shopee Drive + Lainnya) atau hanya salah satunya?
2. **Perilaku harian vs akumulatif:** Apakah target/hitungan di-reset jam 00:00 otomatis atau mengikuti jam kerja driver (mis. 04:00–03:59)?
3. **Penyimpanan:** Apakah cukup LocalStorage (`ojoltrack_*` baru) atau butuh backend/sync? (Rekomendasi: tetap LocalStorage untuk MVP PWA)
4. **Visual:** Di mana user paling ingin melihat feature ini — Dashboard (home), halaman Grafik, atau halaman baru (mis. `/target`)?
5. **Notifikasi (jika relevan):** Apakah boleh minta izin Notification, atau cukup in-app reminder saat buka aplikasi?
6. **Data lama:** Bagaimana jika driver sudah punya 30+ hari data — apakah feature harus hitung mundur dari data lama atau mulai hari ini saja?
7. **Batasan MVP:** Dari Opsi A-G di atas, mana 1 yang paling ingin kamu wujudkan duluan? Atau kamu punya ide lain di luar daftar? Jelaskan dengan 1 kalimat: "Saya ingin ... agar ..."

## 4. Dependency & Risk

| Dependency | Dampak jika tidak siap |
|------------|------------------------|
| LocalStorage key baru `ojoltrack_*` belum ada UI migrasi | Risk: data lama tetap aman (append-only), tapi perlu versioning jika ubah enum Platform/Kategori |
| Serwist/PWA notification permission (untuk Opsi B) | Risk: iOS PWA tidak support background notification — fallback ke in-app toast |
| Recharts SSR dynamic (sudah ada pattern di `app/grafik/page.tsx`) | Reuse pattern yang sama untuk grafik baru — low risk |
| `zod` validation di `storage.ts` | Jika Opsi D (custom string) dilonggarkan, perlu test import/export existing |
| `lib/calc.ts` invariant `calcRpPerKm` | Semua feature baru tidak boleh override `rp_per_km` manual — reuse function |

### Risiko Utama & Mitigasi
- **Scope creep karena request "feature baru" masih abstrak** → Mitigasi: pakai template IDD di §3, require user pilih 1 opsi sebelum coding (sesuai `merge_gate: plan approved` di kanban).
- **Schema breaking** (Opsi D) → Mitigasi: mulai dengan opsi non-breaking (A/B/E/F), tunda D sampai ada demand nyata.
- **PWA storage quota** (~5MB) → Mitigasi: semua feature baru harus tetap lean; reminder/target hanya simpan <1KB, bukan duplikat transaksi.
- **Over-engineering gamifikasi** → Mitigasi: derived dari `Transaksi` saja, jangan tambah write-path baru.
- **Testing offline** → Mitigasi: semua feature baru wajib test `offline → reload → data tetap` seperti demo flow existing.
